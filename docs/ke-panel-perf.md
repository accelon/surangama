# 右欄「科判」節點越來越慢、瀏覽器掛掉——調查與修法

2026-11-12 回報：「點右欄的 科判 節點就很慢很慢，然後瀏覽器掛掉。」
結論：**既有缺陷，與 P2' 重切與網址狀態改動無關**（A/B 量過，見下）。已修並補了永久驗收。

## 一、根因（三層疊加）

`zhu-combined/app.js` 的 `renderKe()` 每次呼叫都把整個面板重組一遍：

| 內容 | 數量（楞嚴，子璿家） |
|---|---:|
| `.ke-node`（科文節點按鈕） | **2,282 顆**，每顆各掛一個 `click` listener |
| `.ke-jump`（分節按鈕，來自 `D.keTree`） | 758＋ 顆，也各掛 listener |
| `keRowsHtml(cur.text)` 科文行 | 2,559 行（換到交光家 3,955 行） |
| `#cards` 的 HTML 字串 | **601 KB**（交光 788 KB） |
| DOM 節點 | 955 → **14,240**（交光 19,827） |

而 `selectUnit()` 桌面路徑會走 `openPanel(state.tab)` → `renderBody` → `renderKe`，
所以**每點一次節點就重建一次這一大塊**。連點 20 下：

```text
牆鐘 3,296ms 之內主執行緒被長任務卡住 2,433ms（74%）
長任務 24 次，其中 23 次 ≥ 50ms，最單次 308ms
heap 在 14～56 MB 間反覆跳（每次重建 2,282＋顆按鈕的分配與回收）
```

手機或記憶體小的裝置再慢 4–6 倍，連點幾次就是「很慢很慢，然後分頁掛掉」。

## 二、修法（不改外觀、不改行為）

`app.js` 三道一起上：

1. **同一家不重繪**：`keRendered` 記住現在畫的是哪家；選句換分只做 `keHighlight()`
   （換 `.ke-jump.on` 的 class），不再重組 60 萬字元。
2. **事件委派**：`keBindOnce()` 在 `#cards` 上綁一組（click／change／toggle 捕獲），
   取代每筆各掛 listener——由 3,000 個降到 3 個。
3. **清單分批**：`.ke-nodes` 收合時**根本不放節點**（原本 2,282 顆就在 DOM 裡）；
   展開時渲染前 400 筆＋「載入更多（還有 N 筆）」，每按再補 400 筆。
   `KE_NODE_PAGE = 400` 是常數，要改一行即可。

## 三、效果（同一支探針、同一口徑）

口徑定義：`syncMs`＝click 同步阻塞；`settleMs`＝DOM 連續兩次取樣不再變動；
`longTaskMs`＝PerformanceObserver 記的主執行緒阻塞總量。

| 情境 | 未修（線上 22:06 版） | 修好後 |
|---|---:|---:|
| 點一個科判節點（同步） | 74～260ms，中位 90ms | **7～16ms，中位 9ms** |
| 20 連點的長任務總量 | 2,433ms／24 次 | **740ms／7 次** |
| 12 連點（驗收腳本口徑） | — | 213～243ms／2 次 |
| DOM 節點（清單收合） | 14,240 | **11,952～12,357** |
| `.ke-node` 按鈕 | 2,282 | 展開時 400（＋載入更多） |
| heap | 14～59 MB 反覆跳 | 54MB 穩定（增減 0） |
| `replaceState` | 2 次／1–2ms（合計 5–9ms） | 同，非熱點 |

**已排除的嫌疑**（都量過，不是這些）：`history.replaceState`（桌面 0.3–1.3ms、手機×6 也才 3.7–8ms）、
`noteRange`／讀更多的延伸計算、P2' 資料（聯集覆蓋變大但每段仍是一次字串拼接）、
科判家差異（各家 44–117ms，沒有某家特别爆）、記憶體洩漏（連點後 heap 回落，無增长）。

## 四、我自己的量測錯誤（記著，下次別再犯）

第一輪我把探針自己的 `await sleep(1600)` 算進「點擊成本」，因此报出「每次 1.7 秒」——
實際是 90ms 上下。**量測裡任何等待都要放在計時之外**，否則等於把探針的睡眠當成產品的延遲。
改口徑後才看到真實數字，也才找出「連點」這個真正的致命手法。
另外两次探針缺陷：① 把隱藏的 `#keBtn` 當成「有科判分頁」（金剛經因此被誤判 fail）；
② 重繪後還拿舊節點比 class（`on:false` 假故障）。兩個都已在腳本裡修掉。

## 五、驗收（新增，永久）

`node zhu-combined/build/cdp-ke-panel.mjs <file:// 或 https:// 頁面>`，10 項：

- 科判分頁有內容；**清單收合時不渲染全部 2,282 筆**
- 展開只第一批 ≤400 且有「載入更多」；按了補下一批
- 點節點 → 選到那一句（`state.selected` 與 `.sent.sel` 都對）
- 連點 12 次長任務合計 ≤ 1,200ms（防退門檻）
- 切走再回科判分頁不重建（長任務 ≤ 300ms）
- 點分節按鈕換分＋高亮跟對；全程無 console 錯誤
- 沒有 `D.ke` 的頁面（金剛經）**明著跳過**，不冒充通過

同時重跑：`cdp-url-state.mjs` 60 項、`cdp-note-more.mjs` 13 項，全綠。

## 六、還沒做／可再優化

1. **`keRowsHtml(cur.text)` 一次畫整本科文**（2,559～3,955 行）：這是剩下的 11k～12k DOM 主體。
   可以照節點清單的做法分批（先給目前這分附近 ±，其餘「載入更多」），
   但那是明顯的 UX 變化（科文從「整本可捲」變成「分段展開」），要做先說。
2. `KE_NODE_PAGE=400` 可調；手機上或可降到 200。
3. `hashchange`／`popstate`（同一分頁貼連結不動）已修並驗過：`app.js` 的 `applyUrl()` 處理
   `u`／`sec`／`tab`，並派 `zhu:hash` 事件給科判層；`kepan.js` 的 `applyUrl()` 接 `kb`／`k`／`rd`／`pg`。
   實測「同頁換 hash」與「重新載入」結果一致（`ed=X273`、`k=0`、`u=46`、`tab=ke`、`sel=1`）。
4. **2026-11-12 23:31 已部署兩站**：線上 `cdp-ke-panel` 11 項、`cdp-url-state` 30 項、`cdp-note-more` 13 項全綠，同頁換 hash 已會還原。

## 七、追記：同晚回報「右欄 科文節點 跳不了正文」

重現調查（`build/_probe-kenav.mjs`、`_probe-kenav2.mjs`；比對線上 22:06 版與本機新版、桌面 1440 與手機 390）：

| 檢查 | 結果 |
|---|---|
| 點節點後 `state.selected`／`.sent.sel` | 兩版四種情境都正確（66→sec 12、249→sec 68、46→sec 2） |
| 目標句在不在視窗內 | 在（`top` 214～218） |
| `D.keNodes` 的 `u` 對不對得到現行句子 | **2,282 個全部對得到**（0 個落空；u 範圍 46–3,731，句子無缺口） |
| 手機 390×844 | 面板自動收起、目標在視窗內 ✓ |
| 尚未選句就開「科判」分頁 | **面板是空的**（只有佔位文字）——最接近「跳不了」的真實可觸發路徑 |

查出來兩件事，都已處理：

1. **無感**：`D.keNodes` 有 **750 個 `u` 重複**（同一句掛 2～4 個科文，例：u=46 同時是「題目」與「本文」）。
   點第二筆時位置本來就對，`selectUnit` 沒有可見變化，看起來就像「點了沒反應」。
   修法：點 `.ke-node` 一律 `scrollIntoView({block:'center'})`＋閃一下（與辭典、書籤跳轉同一套），
   驗收再加「目標在視窗內＋帶 `flash`」一項（`cdp-ke-panel.mjs` 現 11 項）。
2. **`.flash` 的樣式一直不存在**：`app.js` 從搜尋／辭典跳轉時就加 `flash` class，但 `style.css`
   沒有對應規則（只有 kepan 的 `.kb-flash`），等於從來沒閃過。已補 `.flash` 與暗色版 `@keyframes`。

另記一筆：「沒選句時科判分頁是空的」屬既有行為（`renderBody` 需要 u）。要不要像 `#keBtn`
那樣自動挑本分第一句，是 UX 取捨，等作者定。

後續判定：「跳不了」與「慢／掛掉」是同一件事——長任務把點擊堵在後面。**2026-11-12 23:31 已部署兩站**，線上重跑 ke-panel 11 項、url-state 30 項、note-more 13 項全綠。

## 八、後續：這個分頁在同晚被取消

作者判定「buggy、用處不大」，2026-11-12 決定拿掉右欄「科判」分頁。做法是在資料面關掉：`build/to-reader.mjs` 的 `WITH_KE_PANEL = false`。閱讀器本来就「資料有才長分頁」（`buildTabs` 與 `#keBtn` 都看 `D.ke`），所以共用程式一行沒改、其他工作區不受影響；單檔 5,243,672 → 5,085,784 bytes。

- 功能沒消失：上方科文條（麵包屑／經文上的科文標記／科判目錄浮層）走 KEPAN，10 家可切、點了跳正文。
- 舊連結帶 `tab=ke` 不會壞：分頁以「按鈕真的存在」為準，落回 `works`，`u`／`sec`／`kb`／`k` 照樣還原（實測）。
- 本檔 §一～§三 的效能修法（不重繪、事件委派、清單分批）留在閱讀器共用程式裡：其他工作區若餵 `D.ke` 仍走這套渲染，11 項驗收（`cdp-ke-panel.mjs`）也會自動開始跑；楞嚴這一頁現在被標成「這一頁沒有科判分頁」而跳過——是明著的，不是默過。
- 部署：2026-11-12 23:57（主站）與 23:58（鏡像）已發布，5,085,784 bytes；線上驗回科判分頁已不在、url-state 30 項全綠。
